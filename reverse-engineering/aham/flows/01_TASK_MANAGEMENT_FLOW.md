## 1. Overview

### What Are Tasks?

Tasks are approval requests generated by the hospital's back-office systems (billing, pharmacy, finance). When someone creates an invoice, issues a refund, or requests a high-value medication, the system does NOT auto-approve it. Instead, it creates a **jBPM workflow task** that lands in a queue for authorized approvers.

The AHAM mobile app is the front-end for these approvers. They open the app, see pending tasks, claim one, review the details, and either approve or reject it.

### Why Tasks Exist

Hospital billing involves money, compliance, and audit trails. Every financial document (invoice, receipt, refund, discount) requires human sign-off before it becomes final. The jBPM engine enforces who can approve, prevents self-approval, and maintains an audit log of every action.

### The 13 Approval Types -- Registry

There are exactly 13 task types. Each has a `taskName` string that comes from jBPM. The app routes each type to one of 7 detail screens.

```
TASK TYPE REGISTRY
==================

 #  | taskName (exact string from API)         | Category      | Detail Screen
----+------------------------------------------+---------------+------------------------------
  1 | Invoice Generation Approval              | Invoice       | InvoiceDetailScreen
  2 | Discount Approval                        | Invoice       | InvoiceDetailScreen
  3 | Receipt Approval                         | Receipt       | ReceiptDetailScreen
  4 | Receipt Cancellation                     | Receipt       | ReceiptDetailScreen
  5 | Refund Approval                          | Refund        | RefundDetailScreen
  6 | Reversal Invoice Approval                | Invoice       | InvoiceDetailScreen
  7 | Retrospect Invoice Initiation            | Invoice       | InvoiceDetailScreen
  8 | Retrospect Invoice Approval              | Invoice       | InvoiceDetailScreen
  9 | UnBilled Invoice Approval                | Unbilled      | UnbilledDocumentDetailScreen
 10 | HighValue MedicationRequest Approval     | Medication    | HighValueDetailScreen
 11 | Authorization Approval                   | Authorization | AuthorizationDetailScreen
 12 | Mandatory Brand Approval                 | Medication    | LchmDetailScreen
 13 | Invoice Cancellation                     | Invoice       | InvoiceDetailScreen
```

**Key insight:** 6 of the 13 types share `InvoiceDetailScreen`. The screen adapts its layout based on the `taskName`. This is intentional -- they all deal with invoice data but show different subsets of fields.

## 2. User Journey

This is the complete step-by-step path a user takes from opening the task list to completing an action.

### Happy Path: Claim and Approve

```
Step 1: User opens Task Management module
        -> App dispatches LoadModuleTask(queueType: "GROUP", page: 0, size: 20)
        -> TaskBloc emits TaskLoadingState
        -> API call: GET /mdm/api/jbpm/tasks/group?page=0&size=20&unitCode=HYD01
        -> TaskBloc emits TaskFetched(tasks: [...], totalCount: 47, queueType: "GROUP")
        -> Screen renders task list with 20 items

Step 2: User taps a task card (e.g., "Invoice Generation Approval - INV-2026-001")
        -> App dispatches LoadTaskDetail(taskId: 12345)
        -> TaskDetailBloc emits TaskDetailLoadingState
        -> Two parallel API calls:
           a) GET /api/jbpm/tasks/12345/process-variable
           b) GET /amb/invoicelite?documentNo=INV-2026-001  (determined by taskName)
        -> TaskDetailBloc emits TaskDetailLoadedState(task, processVariables)
        -> Detail screen renders with all invoice fields

Step 3: Task is in OPEN state, so "Claim" button is visible
        -> User taps "Claim"
        -> Confirmation dialog: "Would you like to claim the task?" [Cancel] [Claim]
        -> User taps "Claim"
        -> App dispatches ClaimButtonPressed(taskId: 12345, userId: "rohit.g")
        -> TaskDetailBloc emits TaskActionSavingState
        -> API call: POST /api/jbpm/tasks/12345/claim-start { "userId": "rohit.g" }
        -> Response 200: { "taskStatus": "IN_PROGRESS", "actualOwner": "rohit.g" }
        -> TaskDetailBloc emits TaskActionSucessState(taskId: 12345, message: "Task claimed")
        -> UI updates: "Claim" button disappears, "Approve" / "Reject" / "Revert" appear

Step 4: User reviews the invoice details (amounts, line items, patient info)

Step 5: User taps "Approve"
        -> NO confirmation dialog for approve (direct action)
        -> App dispatches ApproveORRejectButtonPressed(taskId: 12345, approved: true)
        -> TaskDetailBloc emits TaskActionSavingState
        -> API call: executeWorkflow with approved=true
        -> jBPM completes the task, status -> DONE
        -> TaskDetailBloc emits TaskActionSucessState(message: "Task approved successfully")
        -> App navigates back to task list
        -> App dispatches RefreshTasksEvent to reload the list
```

### Alternate Path: Reject (Remarks Required)

```
Step 5-alt: User taps "Reject"
        -> Remarks bottom sheet slides up
        -> User MUST type remarks (field is mandatory)
        -> If user taps "Submit" with empty remarks:
           -> Client-side error: "Please enter remarks"
           -> No API call made
        -> User types "Incorrect amount on line item 3" and taps "Submit"
        -> App dispatches ApproveORRejectButtonPressed(
             taskId: 12345, approved: false, remarks: "Incorrect amount on line item 3"
           )
        -> API call: executeWorkflow with approved=false, remarks
        -> jBPM completes the task, status -> DONE/CLOSED
        -> TaskDetailBloc emits TaskActionSucessState(message: "Task rejected")
        -> Navigate back, refresh list
```

### Alternate Path: Revert (Unclaim)

```
Step 5-alt2: User decides they cannot handle this task
        -> User taps "Revert"
        -> Confirmation dialog: "Do you want to revert task?" [Cancel] [Revert]
        -> User taps "Revert"
        -> App dispatches RevertButtonPressed(taskId: 12345, userId: "rohit.g")
        -> TaskDetailBloc emits RevertActionLoading
        -> API call: POST /amb/api/jbpm/tasks/12345/release { "userId": "rohit.g" }
        -> Response 200: { "taskStatus": "OPEN", "actualOwner": null }
        -> TaskDetailBloc emits RevertActionState(message: "Task has been reverted")
        -> Navigate back, refresh list
        -> Task reappears in Group Tasks queue (now claimable by others)
```

### Error Path: Concurrent Claim (409)

```
Step 3-err: Two users try to claim the same task simultaneously
        -> User A taps "Claim" -> API call succeeds -> task is now IN_PROGRESS for User A
        -> User B taps "Claim" -> API call: POST /api/jbpm/tasks/12345/claim-start
        -> Response 409: { "message": "Task has been already claimed by other user..!!" }
        -> TaskDetailBloc emits TaskActionError("Task has been already claimed by other user..!!")
        -> Snackbar shows error message
        -> NO retry attempted (this is by design)
        -> User B navigates back, task no longer in Group Tasks
```

## 4. Task Lifecycle State Machine

### State Diagram

```
                          claim-start (POST)
                 +------------------------------+
                 |                              |
                 v                              |
    +--------+       +-----------+       +-------------+
    |  OPEN  | ----> |  CLAIMED  | ----> | IN_PROGRESS |
    +--------+       | (transit) |       +-------------+
        ^            +-----------+            |
        |                                     |
        |         release (POST)              |
        +-------------------------------------+
                                              |
                          approve/reject      |
                          (executeWorkflow)   |
                                              v
                                         +--------+
                                         |  DONE  |
                                         +--------+
                                              |
                                              | (automatic)
                                              v
                                         +--------+
                                         | CLOSED |
                                         +--------+
```

### Transition Table

```
From          | To           | Trigger          | API Call                               | Guard Conditions
--------------+--------------+------------------+----------------------------------------+----------------------------------
OPEN          | IN_PROGRESS  | claim-start      | POST /jbpm/tasks/{id}/claim-start      | 1. Task not already claimed (409)
              |              |                  |                                        | 2. User must be in task's group
IN_PROGRESS   | DONE         | approve          | executeWorkflow(approved=true)          | 1. Not the document creator (403)
              |              |                  |                                        | 2. Refund mode set (if refund)
              |              |                  |                                        | 3. Retro stage 2: not stage 1 approver
IN_PROGRESS   | DONE/CLOSED  | reject           | executeWorkflow(approved=false)         | 1. Remarks must be non-empty
IN_PROGRESS   | OPEN         | release/revert   | POST /jbpm/tasks/{id}/release           | (no guards)
DONE          | CLOSED       | (automatic)      | (jBPM internal)                        | (system-driven, no user action)
```

### Guard Condition Details

**Guard 1: Concurrent Claim (409)**
- Scenario: User A and User B both see the same OPEN task. User A claims it first.
- When User B tries to claim, the server returns HTTP 409.
- Error message: `"Task has been already claimed by other user..!!"`
- App behavior: Show error snackbar. Do NOT retry. Navigate back.

**Guard 2: Self-Approval (403)**
- Scenario: The person who created the invoice tries to approve it.
- Server compares `createdBy` with `currentUser`.
- Error message: `"Document creator cannot approve the document. Please revert the task."`
- App behavior: Show error snackbar. User must tap "Revert" to release the task.

**Guard 3: Refund Mode Missing (400)**
- Scenario: Refund task where the refund mode (Cash/Cheque/NEFT) was not set in the source system.
- Error message: `"Cannot approve document, Refund mode is not available. Please revert the task."`
- App behavior: Show error snackbar. User must revert.

**Guard 4: Retrospect Stage Conflict (server-enforced)**
- Scenario: For Retrospect Invoice Approval (Type 8), the person who approved Stage 1 cannot be the Stage 2 approver.
- This is enforced server-side. The app does not need to check this locally.

### CLAIMED State -- Implementation Note

The `CLAIMED` state is **transitional**. The `claim-start` endpoint atomically claims AND starts the task. The app never sees a task in `CLAIMED` state. From the app's perspective, a task goes directly from `OPEN` to `IN_PROGRESS`. However, jBPM internally transitions through CLAIMED. This matters if you are debugging jBPM logs.

## 5. BLoC Architecture

### 5.1 TaskBloc (List Screen)

**Purpose:** Manages the task list for all three queues. Handles pagination, filtering, and refresh.

#### Events

```dart
// Base event
abstract class TaskEvent {}

// Load tasks for a specific queue with pagination and filters
class LoadModuleTask extends TaskEvent {
  final String queueType;   // "PERSONAL", "GROUP", "ALL"
  final int page;            // 0-indexed
  final int size;            // default 20
  final TaskFilter? filters; // optional filter object
}

// Pull-to-refresh: resets page to 0 and reloads
class RefreshTasksEvent extends TaskEvent {
  final String queueType;
}
```

#### States

```dart
abstract class TaskState {}

class TaskInitialState extends TaskState {}

class TaskLoadingState extends TaskState {}

class TaskFetched extends TaskState {
  final List<Task> tasks;
  final int totalCount;
  final String queueType;
}

class TaskErrorState extends TaskState {
  final String message;
}
```

#### State Machine Diagram

```
                LoadModuleTask
TaskInitialState ──────────────> TaskLoadingState
                                      |
                            +---------+---------+
                            |                   |
                       (success)            (failure)
                            |                   |
                            v                   v
                      TaskFetched         TaskErrorState
                            |                   |
              LoadModuleTask|     LoadModuleTask |
              (next page)   |                   |
                            v                   v
                      TaskLoadingState    TaskLoadingState
```

#### BLoC Implementation Pattern

```dart
class TaskBloc extends Bloc<TaskEvent, TaskState> {
  final TaskRepository taskRepository;

  TaskBloc({required this.taskRepository}) : super(TaskInitialState()) {
    on<LoadModuleTask>(_onLoadModuleTask);
    on<RefreshTasksEvent>(_onRefreshTasks);
  }

  Future<void> _onLoadModuleTask(
    LoadModuleTask event,
    Emitter<TaskState> emit,
  ) async {
    emit(TaskLoadingState());

    try {
      final response = await _fetchTasksByQueue(
        queueType: event.queueType,
        page: event.page,
        size: event.size,
        filters: event.filters,
      );

      emit(TaskFetched(
        tasks: response.taskSummaryList,
        totalCount: response.totalCount,
        queueType: event.queueType,
      ));
    } catch (e) {
      emit(TaskErrorState(message: e.toString()));
    }
  }

  Future<TaskListResponse> _fetchTasksByQueue({
    required String queueType,
    required int page,
    required int size,
    TaskFilter? filters,
  }) async {
    switch (queueType) {
      case "PERSONAL":
        return taskRepository.fetchPersonalTasks(page, size, filters);
      case "GROUP":
        return taskRepository.fetchGroupTasks(page, size, filters);
      case "ALL":
        return taskRepository.fetchAllTasks(page, size, filters);
      default:
        throw Exception("Unknown queue type: $queueType");
    }
  }

  Future<void> _onRefreshTasks(
    RefreshTasksEvent event,
    Emitter<TaskState> emit,
  ) async {
    // Reset to page 0 with current filters
    add(LoadModuleTask(
      queueType: event.queueType,
      page: 0,
      size: 20,
    ));
  }
}
```

#### BLoC Implementation Pattern

```dart
class TaskDetailBloc extends Bloc<TaskDetailEvent, TaskDetailState> {
  final TaskRepository taskRepository;
  final TaskService taskService;

  TaskDetailBloc({
    required this.taskRepository,
    required this.taskService,
  }) : super(TaskDetailInitialState()) {
    on<LoadTaskDetail>(_onLoadTaskDetail);
    on<ClaimButtonPressed>(_onClaimTask);
    on<ApproveORRejectButtonPressed>(_onApproveOrReject);
    on<RevertButtonPressed>(_onRevertTask);
    on<ShowRevertActionDialogBox>(_onShowRevertDialog);
  }

  Future<void> _onLoadTaskDetail(
    LoadTaskDetail event,
    Emitter<TaskDetailState> emit,
  ) async {
    emit(TaskDetailLoadingState());

    try {
      // Two parallel API calls
      final results = await Future.wait([
        taskService.getProcessVariables(event.taskId),
        _fetchDocumentDetails(event.taskId),
      ]);

      final processVariables = results[0] as Map<String, dynamic>;
      final task = results[1] as Task;

      emit(TaskDetailLoadedState(
        task: task,
        processVariables: processVariables,
      ));
    } catch (e) {
      emit(TaskDetailLoadingErrorState(message: e.toString()));
    }
  }

  Future<void> _onClaimTask(
    ClaimButtonPressed event,
    Emitter<TaskDetailState> emit,
  ) async {
    emit(TaskActionSavingState());

    try {
      final response = await taskService.claimAndStartTask(
        event.taskId,
        event.userId,
      );
      emit(TaskActionSucessState(
        taskId: event.taskId,
        message: response.message,
      ));
    } catch (e) {
      emit(TaskActionError(message: e.toString()));
    }
  }

  Future<void> _onApproveOrReject(
    ApproveORRejectButtonPressed event,
    Emitter<TaskDetailState> emit,
  ) async {
    // Client-side validation for reject
    if (!event.approved && (event.remarks == null || event.remarks!.isEmpty)) {
      emit(TaskActionError(message: "Please enter remarks"));
      return;
    }

    emit(TaskActionSavingState());

    try {
      // Route to the correct executeWorkflow method based on task type
      await _executeWorkflowByType(event);
      emit(TaskActionSucessState(
        taskId: event.taskId,
        message: event.approved ? "Task approved successfully" : "Task rejected",
      ));
    } catch (e) {
      emit(TaskActionError(message: e.toString()));
    }
  }

  Future<void> _onRevertTask(
    RevertButtonPressed event,
    Emitter<TaskDetailState> emit,
  ) async {
    emit(RevertActionLoading());

    try {
      final response = await taskService.releaseTask(
        event.taskId,
        event.userId,
      );
      emit(RevertActionState(
        taskId: event.taskId,
        message: "Task has been reverted",
      ));
    } catch (e) {
      emit(TaskActionError(message: e.toString()));
    }
  }
}
```

### 5.4 Screen Routing by Task Name

```dart
Widget _buildDetailScreen(String taskName) {
  switch (taskName) {
    case "Invoice Generation Approval":
    case "Discount Approval":
    case "Reversal Invoice Approval":
    case "Retrospect Invoice Initiation":
    case "Retrospect Invoice Approval":
    case "Invoice Cancellation":
      return InvoiceDetailScreen(taskName: taskName);

    case "Receipt Approval":
    case "Receipt Cancellation":
      return ReceiptDetailScreen(taskName: taskName);

    case "Refund Approval":
      return RefundDetailScreen();

    case "UnBilled Invoice Approval":
      return UnbilledDocumentDetailScreen();

    case "HighValue MedicationRequest Approval":
      return HighValueDetailScreen();

    case "Authorization Approval":
      return AuthorizationDetailScreen();

    case "Mandatory Brand Approval":
      return LchmDetailScreen();

    default:
      return TaskDetailFallbackScreen(taskName: taskName);
  }
}
```

### Type 1: Invoice Generation Approval

**What it is:** A new invoice has been created. An approver must verify amounts before it becomes official.

```
--------------+-----------------+------------------------------------
```

### Pagination

- **Page size:** 20 items per page.
- **Infinite scroll:** When user scrolls near the bottom, dispatch `LoadModuleTask` with `page + 1`.
- **Pull-to-refresh:** Dispatches `RefreshTasksEvent`, which resets page to 0.
- **Total count:** Returned in API response. Use to determine if more pages exist.

```dart
// Infinite scroll detection in ListView
bool _shouldLoadMore(ScrollNotification notification) {
  if (notification is ScrollEndNotification) {
    final metrics = notification.metrics;
    if (metrics.pixels >= metrics.maxScrollExtent - 200) {
      // 200px before end, trigger next page
      final currentPage = _loadedItems ~/ 20;
      if (_loadedItems < _totalCount) {
        context.read<TaskBloc>().add(
          LoadModuleTask(
            queueType: _currentQueue,
            page: currentPage + 1,
            size: 20,
            filters: _currentFilters,
          ),
        );
      }
    }
  }
  return false;
}
```

### Pagination Append vs Replace Logic

```
When page == 0: REPLACE the entire list (new search / filter / refresh).
When page > 0:  APPEND to the existing list (infinite scroll).
```

In the BLoC, you need to track accumulated tasks:

```dart
Future<void> _onLoadModuleTask(
  LoadModuleTask event,
  Emitter<TaskState> emit,
) async {
  // Only show full loading indicator for page 0
  if (event.page == 0) {
    emit(TaskLoadingState());
  }

  try {
    final response = await _fetchTasksByQueue(...);

    List<Task> allTasks;
    if (event.page == 0) {
      allTasks = response.taskSummaryList;
    } else {
      // Append to existing list
      final currentState = state;
      if (currentState is TaskFetched) {
        allTasks = [...currentState.tasks, ...response.taskSummaryList];
      } else {
        allTasks = response.taskSummaryList;
      }
    }

    emit(TaskFetched(
      tasks: allTasks,
      totalCount: response.totalCount,
      queueType: event.queueType,
    ));
  } catch (e) {
    emit(TaskErrorState(message: e.toString()));
  }
}
```

## 12. Error Handling Matrix

### Complete Error Catalog

```
 #  | HTTP | Error Message                                                              | Trigger                              | App Response
----+------+----------------------------------------------------------------------------+--------------------------------------+------------------------------------------
  1 | 409  | "Task has been already claimed by other user..!!"                          | Concurrent claim                     | Snackbar, NO retry, stay on screen
  2 | 403  | "Document creator cannot approve the document. Please revert the task."    | Self-approval attempt                | Snackbar, user must revert
  3 | 400  | "Cannot approve document, Refund mode is not available. Please revert..."  | Refund without mode                  | Snackbar, user must revert
  4 | 404  | "Task not found"                                                           | Task deleted/completed elsewhere     | Snackbar, navigate back
  5 | 5xx  | "Failed to claim task"                                                     | Server error on claim                | Snackbar, user can retry manually
  6 | 5xx  | "Failed to approve task"                                                   | Server error on approve              | Snackbar, user can retry manually
  7 | 5xx  | "Failed to reject task"                                                    | Server error on reject               | Snackbar, user can retry manually
  8 | 5xx  | "Failed to revert task"                                                    | Server error on revert               | Snackbar, user can retry manually
  9 | N/A  | "Please enter remarks"                                                     | Empty remarks on reject (client)     | Inline error, no API call
 10 | 200  | "Task has been reverted"                                                   | Successful revert (info, not error)  | Snackbar (info), navigate back
 11 | 403  | "Unauthorized to perform this action"                                      | Insufficient permissions             | Snackbar, navigate back
 12 | N/A  | "Please select a user to reassign"                                         | Reassign without selection (client)  | Inline error, no API call
```

### Retry Policy

```
Error Type          | Retry?                    | Details
--------------------+---------------------------+--------------------------------------------
409 (claim conflict)| NO                         | Task is gone. Do not retry.
403 (self-approval) | NO                         | User must revert. Cannot be retried.
400 (refund mode)   | NO                         | Data problem. Cannot be retried in app.
404 (not found)     | NO                         | Task no longer exists.
401 (unauthorized)  | AUTO (token refresh)       | Auth interceptor handles this silently.
5xx (server error)  | YES, 3x exponential backoff| Wait 1s, 2s, 4s. Then show error.
Network error       | YES, 3x exponential backoff| Same as 5xx.
Client-side         | N/A                        | Fix input and resubmit.
```

### Error Handling Implementation Pattern

```dart
// In the HTTP interceptor / repository layer:

Future<T> _withRetry<T>(Future<T> Function() apiCall, {int maxRetries = 3}) async {
  int attempt = 0;
  while (true) {
    try {
      return await apiCall();
    } on DioException catch (e) {
      attempt++;

      // Do NOT retry client errors (4xx)
      if (e.response != null && e.response!.statusCode! < 500) {
        rethrow;
      }

      // Retry server errors (5xx) and network errors
      if (attempt >= maxRetries) {
        rethrow;
      }

      // Exponential backoff: 1s, 2s, 4s
      await Future.delayed(Duration(seconds: math.pow(2, attempt - 1).toInt()));
    }
  }
}

// 401 handling in interceptor:
interceptor.onError = (error) async {
  if (error.response?.statusCode == 401) {
    // Attempt token refresh
    final newToken = await authService.refreshToken();
    if (newToken != null) {
      // Retry original request with new token
      error.requestOptions.headers['Authorization'] = 'Bearer $newToken';
      return handler.resolve(await dio.fetch(error.requestOptions));
    } else {
      // Token refresh failed, redirect to login
      navigatorKey.currentState?.pushReplacementNamed('/login');
    }
  }
};
```

## 13. Edge Cases

### 13.1 Concurrent Claim Race Condition

**Scenario:** User A and User B both view the same OPEN task in Group Tasks. Both tap "Claim" within seconds.

**What happens:**
1. User A's request arrives first. Server claims the task for User A. Returns 200.
2. User B's request arrives second. Server sees task is already claimed. Returns 409.
3. User B sees: "Task has been already claimed by other user..!!"
4. User B navigates back. On refresh, the task is gone from Group Tasks (it is now in User A's My Tasks).

**Implementation note:** Do NOT attempt to lock the task client-side. The server is the single source of truth. Accept the 409 gracefully.

### 13.2 Self-Approval Detection

**Scenario:** User claims a task. When they try to approve, the server detects that `createdBy == currentUser`.

**What happens:**
1. Claim succeeds (the system allows you to claim your own document -- you might want to review it).
2. Approve fails with 403: "Document creator cannot approve the document."
3. User's only option is to Revert the task so someone else can approve it.

**Why not block at claim time?** Because claiming is useful for review even if you cannot approve. The business logic is: you CAN look at your own document, you just CANNOT approve it.

### 13.3 Token Expiry Mid-Action

**Scenario:** User is on the detail screen. Their JWT token expires. They tap "Approve".

**What happens:**
1. API call returns 401.
2. HTTP interceptor catches 401, attempts silent token refresh.
3. If refresh succeeds: original request is retried transparently. User never sees an error.
4. If refresh fails (refresh token also expired): user is redirected to login screen.

**Implementation note:** The token refresh must be atomic. If multiple concurrent requests all get 401, only ONE refresh should happen. Use a lock or queue pattern in the interceptor.

### 13.4 Network Loss During Action

**Scenario:** User taps "Approve" but the device loses connectivity.

**What happens:**
1. First attempt fails (network error).
2. Automatic retry with exponential backoff: 1s, 2s, 4s.
3. If network returns within the retry window: action completes.
4. If all 3 retries fail: `TaskActionError("Failed to approve task")` is emitted.
5. User sees error snackbar. The task remains in IN_PROGRESS state.
6. User can manually retry by tapping "Approve" again.

**Important:** There is no offline queue. Actions are not stored for later. If all retries fail, the user must retry manually when connectivity is restored.

### 13.5 Stale Task List After Action

**Scenario:** User approves a task and navigates back to the list. The list still shows the now-completed task.

**What happens:**
1. After successful approve/reject/revert, the app dispatches `RefreshTasksEvent`.
2. This resets to page 0 and fetches fresh data from the server.
3. The completed task will no longer appear in the list (it is DONE, not IN_PROGRESS/OPEN).

**Implementation note:** Always dispatch RefreshTasksEvent after navigating back from a successful action. Never rely on local state removal.

### 13.6 Retrospect Two-Stage Approval

**Scenario:** User approves Stage 1 of a retrospective invoice. The same user then tries to approve Stage 2.

**What happens:**
1. Stage 1: User A claims and approves. Task completes.
2. jBPM automatically creates a new task for Stage 2 (Type 8: "Retrospect Invoice Approval").
3. Stage 2 task appears in Group Tasks.
4. User A claims Stage 2 task. Claim succeeds.
5. User A taps "Approve". Server rejects: the Stage 1 approver cannot be the Stage 2 approver.

**Implementation note:** This is entirely server-enforced. The app does not need to track who approved Stage 1. The server compares process variables.

### 13.7 Refund Without Mode

**Scenario:** A refund task was created in the source system without specifying the refund mode (Cash/Cheque/NEFT). An approver tries to approve it.

**What happens:**
1. User claims the refund task. Claim succeeds.
2. User reviews refund details. Refund Mode field shows empty/null.
3. User taps "Approve".
4. Server returns 400: "Cannot approve document, Refund mode is not available. Please revert the task."
5. User must revert. The refund mode must be set in the source system (not in AHAM).

**Implementation note:** The app cannot fix this. The "Refund Mode" field is read-only in the approval screen. The data must be corrected at the source.

### 13.8 Large Task Lists and Pagination

**Scenario:** There are 500+ tasks. User scrolls through multiple pages, then applies a filter.

**What happens:**
1. User has scrolled to page 5 (100 items loaded).
2. User opens filter, selects "Refund Approval", taps Apply.
3. App dispatches `LoadModuleTask(page: 0, size: 20, filters: {taskName: "Refund Approval"})`.
4. Page resets to 0. Previous 100 items are replaced with new filtered results.
5. Total count updates to reflect filtered count (e.g., 12 instead of 500).

**Implementation note:** ALWAYS reset to page 0 when filters change. Never append filtered results to an unfiltered list.

### 13.9 Task Disappears While Viewing

**Scenario:** User is on the detail screen reviewing a task. An admin completes or cancels the task from the web portal.

**What happens:**
1. User is viewing the detail screen (task was loaded successfully).
2. User taps "Approve".
3. Server returns 404: "Task not found" (task was already completed/cancelled).
4. `TaskActionError("Task not found")` is emitted.
5. Snackbar shows error. User navigates back. On refresh, task is gone.

**Implementation note:** There is no WebSocket or push notification for task state changes. The app only discovers the change when it tries to act on the task.

### 13.10 Empty States

Handle these empty states in the UI:
